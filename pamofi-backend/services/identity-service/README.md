# identity-service

Independent build: `npm ci && npm test && npm run build`. Set `DATABASE_URL` to this service’s database before `npm start`. See `../../docs/BUILD_STATUS.md` for the distinction between verified source behavior and deployment qualification.

Apply owned migrations as a separate release step with `DATABASE_URL=... npm run migrate`. The database user must have migration privileges. The local demo uses a single owned login; the [production configuration](../../infra/production/README.md) separates a non-login owner, explicit migration login and restricted runtime login.

`POST /v1/session` creates a customer session after validating `PUBLIC_ORIGIN`; `GET /v1/session` resolves the opaque cookie. New sessions require a 32-byte cryptographically random, unpadded base64url `Idempotency-Key`. A retry without the cookie returns the original cookie and identity for 24 hours; expired or revoked sessions cannot be resurrected. The retry key is a short-lived credential: protect it, never log it, and clear it after the cookie is confirmed. The database stores only hashes of the retry key and session token.

Configure a distinct, secret, persistent `SESSION_CREATION_SECRET` of at least 32 bytes for each environment; do not reuse the demo value. The server derives the cookie using HMAC so it can reissue it without retaining plaintext. Changing that secret while requests are in flight makes their retries unavailable; already issued cookies continue to work. Coordinate rotation after the 24-hour retry period or implement a versioned key ring before production. Set `APP_ENV=demo` only locally. Production requires an HTTPS origin and rejects the demo secret.

`DELETE /v1/session` requires the configured `Origin`, revokes only the current device's session, and clears its cookie after the database update succeeds. The response is idempotent `204` and is not cached. Other sessions and recovery credentials remain valid; a retained creation retry secret cannot revive the revoked session. Before offering sign-out to an anonymous customer, explain that they need their saved recovery reference and key to return to the same account. Clients must clear temporary retry credentials only after logout is confirmed and keep their state intact when the API is unavailable.

## Staff authentication and approval

Staff accounts and cookies are independent of customer accounts. A customer session never grants a staff role. `POST /v1/staff/register` accepts only `{email,password,displayName}` and always returns the same `202 {status:"pending",next:"login"}` for a valid new or duplicate address. It never changes an existing account. Email is a normalized login name; it is **not an email-ownership verification**. An administrator must verify the applicant and their site assignments through the organization's approval process before approving them.

Passwords are 15–128 characters and use salted asynchronous Node `scrypt` with `N=32768,r=8,p=3`, one active hash per process and at most four waiting operations. This is the [OWASP 32 MiB scrypt profile](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt). Unknown accounts use the same hash operation. Five failed password attempts lock that account for 15 minutes; the counter is in PostgreSQL and survives process replacement. Route rate limits add a per-process IP limit. A public deployment should also configure its trusted edge request limit. Proxy trust is off by default. `PAMOFI_TRUST_PROXY_CIDRS` accepts only explicit IP CIDRs with nonzero prefixes, never wildcards, hostnames or universal ranges. The public gateway must overwrite incoming `X-Forwarded-For`; configure only the actual private proxy network. Requests from untrusted peers cannot choose their rate-limit key by forging that header.

`POST /v1/staff/login {email,password}` creates a five-minute, single-use HttpOnly challenge cookie and returns `{staffId,next:"mfa_setup"|"mfa_verify",expiresIn:300}`. This cookie cannot access staff data or privileged APIs. `POST /v1/staff/mfa/setup {}` returns `{staffId,secret,uri,expiresIn}` only for a password-authenticated, unenrolled challenge. Pin the returned staff ID to the login response, so a second tab cannot silently substitute another enrollment. Display the key locally or render a QR code locally; never send it to an external QR service or persist it in browser storage. A retry of setup within that challenge returns the same seed. `POST /v1/staff/mfa/confirm {code}` finishes enrollment. An enrolled user instead calls `POST /v1/staff/mfa/verify {code}`. Match that response and the subsequent `GET /v1/staff/session` to the original staff ID before claiming success; a blocked cookie must not make a previous account look like the newly authenticated one.

TOTP uses the maintained, pinned [OTPAuth](https://github.com/hectorm/otpauth) library and the [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238) 30-second period, six digits and SHA-1 HMAC for authenticator compatibility. Validation permits one adjacent time step in either direction. The accepted counter is stored under a user row lock: concurrent submissions and a later challenge cannot reuse a successfully accepted time step. Each challenge permits five failed codes. Ten failed codes across challenges lock the account for 15 minutes. Keep server time synchronized. A user who just enrolled or signed in may need to wait for the authenticator's next code before signing in again.

MFA seeds are encrypted with AES-256-GCM, a random nonce and authenticated staff-ID binding. Set a separate `STAFF_MFA_ENCRYPTION_KEY` containing **64 hexadecimal characters from 32 random bytes**. The service has no default key and staff endpoints fail closed when it is missing or malformed. Uniform-byte fixture keys are accepted only in explicit demo/development mode. Store the real key separately from database backups and exercise restoration with it. Changing this key without a planned re-encryption of existing seeds makes those accounts unable to authenticate; the current envelope is versioned, but automatic key rotation and a self-service lost-authenticator reset are not implemented. Retain more than one approved administrator and manage authenticator loss through an explicitly reviewed recovery procedure; there is no public MFA bypass.

Successful MFA issues an opaque eight-hour session. Production cookies are `__Host-pamofi_staff_session` and `__Host-pamofi_staff_challenge`, with `Secure`, `HttpOnly`, `SameSite=Lax`, path `/` and no Domain. Demo names start with `pamofi_demo_`. `GET /v1/staff/session` returns `{staffId,email,displayName,status,role,siteIds,version,mfaEnrolled,createdAt,mfaVerified:true}`. A pending applicant can read this status and sign out, but cannot perform staff operations. `DELETE /v1/staff/session` revokes the current session and pending challenge, clears their cookies only after storage succeeds, and leaves other staff and customer sessions intact.

Only an approved administrator with a completed MFA session can read `GET /v1/staff/users`, `GET /v1/staff/audit`, or make role decisions. Both lists return at most 50 records, with `nextCursor` to pass as `?after=UUID`. A decision is `POST /v1/staff/users/:id/decision` with `{expectedVersion,status,role?,siteIds?,reason}`. `status` is `approved`, `rejected`, or `disabled`; a trimmed reason of 5–500 characters is required. Approval requires prior MFA enrollment, a role and explicit site IDs. Administrators have role `admin` and `siteIds:[]`, meaning unrestricted administrative scope. Roles `agent` and `support` require 1–100 distinct approved site UUIDs. The UI must select actual sites from the network authority. Identity does not reach into another service's database to manufacture a cross-service foreign key. Rejection/disable preserve the historical role scope and do not accept a new one.

Decisions serialize, compare `expectedVersion`, increment the version, invalidate **all** target sessions and in-flight MFA challenges, and append an audit event in the same transaction. Stale decisions return `409 staff_changed`. Self-decisions are rejected, and the final approved administrator is protected. `POST /v1/staff/users/:id/revoke-sessions {expectedVersion,reason}` provides an audited administrative all-session revocation without changing the role. Audit rows record actor, target, before/after scope, versions, reason and time; a database trigger rejects updates and deletes. No password, session token or MFA seed is returned in these records.

The private prepaid service resolves a forwarded staff cookie through `GET /internal/v1/staff/session`. It needs an HS256 service JWT with issuer/subject `prepaid-access`, audience `identity`, scope `staff:resolve`, `iat` and `exp`, and maximum age 30 seconds. The response is `{staffId,role,siteIds,version,mfaVerified:true}` only for an approved current session. Pending accounts return `403`; expired/revoked sessions return `401`. `GET /internal/v1/staff/users/:id` instead requires `staff:read` and returns `{staffId,status,role,siteIds,version}` for authoritative allocation checks. Keep both routes behind the private service network/TLS gateway. Browser-supplied role, actor or customer IDs never choose the authenticated identity.

All staff mutations require exact `Origin: PUBLIC_ORIGIN`, every auth response is `Cache-Control: no-store`, and customer and staff cookies remain same-origin. Native/mobile clients must use a same-origin HTTPS gateway and verify cookie establishment. There is no permissive cross-origin credential fallback or token-in-local-storage mode.

## First administrator bootstrap

No migration seeds a staff password, role or MFA bypass. After applying migrations, build the service and run `node dist/bootstrap-staff.js` as a deliberate operator action with a migration-owner database connection. It accepts `--email`, `--display-name`, `--password-file`, and `--reason`; no plaintext password argument is accepted. The password file must be a regular file owned by the operator, mode `0600` or `0400`, containing one 15–128-character password line. Do not commit this file. Supply these explicit acknowledgments in addition to the usual application environment and encryption key:

```text
STAFF_BOOTSTRAP_CONFIRM=first-admin
STAFF_BOOTSTRAP_ENVIRONMENT=<exact APP_ENV: demo, staging, or production>
STAFF_BOOTSTRAP_DATABASE=<exact database name from DATABASE_URL>
```

Demo additionally requires `APP_ENV=demo`, `NODE_ENV=development`, a loopback PostgreSQL URL and `STAFF_BOOTSTRAP_ISOLATED=1`. Staging/production require `NODE_ENV=production`, a canonical HTTPS `PUBLIC_ORIGIN`, and a non-demo encryption key. A bootstrap invocation is:

```bash
node dist/bootstrap-staff.js \
  --email first.operator@example.org \
  --display-name 'First operator' \
  --password-file /run/secrets/first_staff_password \
  --reason 'Approved first administrator under the operator change record'
```

The command takes a database advisory lock, verifies that bootstrap has never completed and that no administrator already exists, and atomically records the first account, immutable audit event and permanent bootstrap guard. It emits only the staff ID and next step. That administrator must still log in and enroll MFA before receiving a staff session. Re-running the command fails even if the initial administrator is later disabled. The flags cannot replace an administrator or reset an authenticator. Securely remove the one-use password file after the operator has stored their credential and verified MFA.

## Captive to system-browser handoff

`POST /v1/handoff {}` with the current customer cookie returns `{handoffCode,expiresIn:120,continueUrl}`. The URL is the clean `${PUBLIC_ORIGIN}/handoff`; it never contains a credential. The customer copies the 43-character code and pastes it into that page in their system browser. Keep the code in memory and require an explicit confirmation before `POST /v1/handoff/redeem {handoffCode}`. A successful response sets a fresh customer cookie for the same account. The client must confirm the returned customer ID with `GET /v1/session` before claiming success, because a browser may block cookies.

Only a hash of the code is stored. Creating another code invalidates the previous unused code from that source session. Redemption atomically consumes the code, checks its two-minute expiry and the original session's validity, and creates the new session. A concurrent retry loses with `401 invalid_handoff`. Revoking the source session invalidates an unused code. A target browser with an existing authenticated customer gets `409 session_already_exists` without consuming the code; the service never silently replaces that account. Handoff leaves the original session and recovery settings intact.

## Verification

Set `PAMOFI_TEST_DATABASE_URL` to this service's isolated migrated database before `npm test` to run integration tests. Without it, database cases are explicitly skipped. The repository's strict `../../local-tools/verify.mjs --integration --browser` gate rejects all skipped integration cases. Identity tests cover bootstrap races, MFA RFC vectors, authenticated encryption, challenge/counter replay, persistent attempt limits, Origin checks, role approvals, concurrent stale decisions, audit immutability, session revocation, handoff races/expiry/account replacement and customer recovery behavior.
