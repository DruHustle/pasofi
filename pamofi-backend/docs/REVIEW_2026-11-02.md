## Follow-up — Vercel, Oracle and the Starlink site path

The owner selected Vercel for the frontend and Oracle for the backend, confirmed that the production MikroTik will sit behind a Starlink router, and explicitly requested completion of the software before physical hotspot tests. The review found three source/configuration gaps: the Vercel build had no server-side API destination, the Oracle gateway assumed its TLS hostname was also the browser origin, and the production Compose stack had no opt-in FreeRADIUS transport package. The software follow-up closes these gaps without activating a physical NAS or a public deployment.

### Software changes

- The web project now includes a server-only Vercel API function with a fixed HTTPS Oracle destination and an explicit public method/path allowlist. It forwards approved customer/staff cookies and idempotency keys, enforces the exact browser Origin, authenticates platform client-IP metadata to Oracle, preserves separate secure Set-Cookie headers and rejects internal routes, redirects, oversized bodies and unsafe upstream responses. It has bounded timeouts, performs no automatic mutation retries and returns non-cacheable API errors when configuration is absent.
- The optional Oracle overlay separates the browser origin from the API TLS hostname. Its gateway authenticates the Vercel proxy credential before accepting a canonical client IP, removes those trust headers before forwarding internally and rejects direct API access. Token generation and preflight use protected files outside the repository; no proxy credential is embedded in the Vite bundle or stored in source.
- The site-link planner prepares a separate outbound MikroTik-to-Oracle WireGuard path with narrow private `/32` peers and no customer default/LAN routes. Its Oracle firewall accounts for Docker's RADIUS port translation, while the router rules scope RADIUS replies and HTTPS management to the service peer. The generated material remains prepared-only and requires inspected addresses, public peer keys, a reviewed host/OCI UDP rule and physical acceptance.
- The opt-in production RADIUS package binds UDP 1812/1813 to the exact private tunnel address and connects FreeRADIUS to a private mutual-TLS network authority. It uses the network runtime database identity, independent certificates, a pinned client identity, protected NAS material and explicit qualification flags. Customer-network authority remains disabled by default.
- Review also removed the network runtime's ability to register or enable NASes or change their site/client/login configuration. The narrow primary-key UPDATE privilege retains PostgreSQL row locking; the production role proof checks denied administration and real credential issuance with an idempotent locked retry. NAS registration remains an owner/migration operation.
- Independent routing review caught two gaps that same-bridge tests would miss: published RADIUS reply traffic and the existing RouterOS HTTPS worker needed explicit Docker routing. Dedicated ingress/control bridges now provide those paths, the transport lab exercises a separate simulated NAS network and observed source addresses, and an optional control overlay mounts protected per-router credentials and public trust files. Its preflight reports prepared-only; the default reconciler remains disabled.
- Operations checks understand separate public Oracle and Vercel origins and reject unexpected public service ports. The only optional RADIUS exception requires the exact private address and both expected UDP bindings; the authority remains unpublished. CI includes the proxy, origin/secret configuration, site-link/firewall, RADIUS transport and split-host production gates alongside the original complete application, database, browser, backup and native build checks.
- Actual CI exposed startup defects that offline configuration checks could not establish: the guarded RADIUS entrypoint needed the pinned executable's absolute path, and the read-only split gateway needed explicit temporary paths for every Nginx module.
