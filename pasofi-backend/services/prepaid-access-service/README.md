# prepaid-access-service

Independent build: `npm ci && npm run build`. Set `DATABASE_URL` to this service's database before `npm start`. `npm test` runs integration tests when `PAMOFI_TEST_DATABASE_URL` points to an isolated database. The outbox case also requires `PAMOFI_TEST_NOTIFICATION_DATABASE_URL` and `PAMOFI_TEST_NOTIFICATION_URL`; run worker tests serially because they claim service-wide queues. A skipped integration case is not an acceptance pass. Source and synthetic tests do not establish deployed provider/router qualification; see `../../docs/BUILD_STATUS.md`.

Apply owned migrations as a separate release step with `DATABASE_URL=... npm run migrate`. The database user must have migration privileges. This local-demo setup does not yet separate runtime and migration roles.

The outbox dispatcher is disabled by default. To run it, configure `OUTBOX_DISPATCH_ENABLED=true`, `NOTIFICATION_URL` and a separate `INTERNAL_EVENTS_SECRET` of at least 32 bytes. Non-demo operation requires HTTPS and rejects the example secret. It retries with a bounded lease and backoff. The notification consumer records a reference-only job, resolves its details through the authenticated delivery boundary, and uses only its explicitly configured mock or qualified Sendai mode. No phone number or voucher enters the outbox payload.

Cash received by an approved agent is the current purchase path. Digital checkout defaults to disabled; the only selectable mode is the local mock, requiring `PAMOFI_PAYMENTS_ENABLED=true`, `PAMOFI_PAYMENT_MODE=mock`, `APP_ENV=demo` and `NODE_ENV=development`. It makes no payment HTTP request or real charge. Production, legacy sandbox and direct-provider flag combinations all remain disabled.

`PAMOFI_PAYMENT_PROVIDER` may be absent for the existing demo configuration or exactly `mock`. Any other explicit value, including an empty value or a real bank/provider name, disables checkout instead of falling back to simulation. Naming CABS, Zimswitch, Stanbic, CBZ, ZB, EcoCash or InnBucks cannot enable a payment integration. See [the payment investigation](../../docs/PAYMENT_INTEGRATION_RESEARCH_2026-11-02.md) for the bank comparison and merchant approval requirements.

Pesepay has been removed from application registration and configuration selection. `PAMOFI_PESEPAY_SANDBOX_ENABLED`, `PESEPAY_*` credentials and qualification flags cannot enable it; `/callbacks/pesepay` returns 404. Historical transactions, entitlements and review records remain intact. The old adapter and callback helper are retained solely for historical contract regressions, without an application route or worker registration.

The active mock worker uses database leases and claims only `provider='mock'` jobs. It cannot check, acknowledge or fulfill historical Pesepay attempts. Migration `026_provider_identity.sql` labels existing simulator attempts only when both their reference and order match a local simulator record; ambiguous historical records are left untouched. Authenticated `/v1/orders/:id/status` and unused-quote closure remain available with checkout disabled. Historical status is the recorded ledger state, not a new provider lookup; unsettled old transactions require explicit investigation.

`src/ecocash.ts` prepares direct EcoCash Online Payments sandbox requests and read-only lookups using the official public contract. It is dormant, has no environment enablement path or callback route, and never returns verified settlement. Even a matched `Charged` response remains `review_required` because the published lookup omits independently verified paid terms. See [DIRECT_PAYMENTS.md](DIRECT_PAYMENTS.md) for verified endpoints, the tested boundary and the merchant/contract inputs still needed. No provider account, real sandbox transaction or live charge has been created by these tests.


## Reconciliation and customer history

Payment review outcomes remain attached to the exact provider charge on retries. A duplicate charge never reports an entitlement it did not create, and a consumed-access reversal remains pending review. A verified reversal observed before success is recorded without granting access; an older success response cannot undo it. A reference conflict also blocks another initiation for that order until investigation. Only the adapter's explicit `verified_success` result can fulfill an order.

`GET /v1/access` shows active access first, the usable FIFO queue next, and historical purchases afterward. Optional `limit` (1–100, default 100) and `offset` (0–1,000,000, default 0) paginate the authenticated customer's records; `hasMore` and `nextOffset` indicate another page. All service responses use `Cache-Control: no-store` so customer history, entitlement data and internal authority responses are not cached.

`GET /v1/orders?requestKey=...` recovers at most one order belonging to the authenticated customer with that exact saved idempotency key (`[A-Za-z0-9_-]`, 16–128 characters). The response includes `customerId`, an explicit `lookupKey` echo and `orders`. This read-only lookup remains available when checkout is disabled or the bundle is unpublished; it never creates a quote or starts a payment. Clients must verify the owner, echoed key and expected bundle before restoring the order, and preserve the saved request if the result is missing or unverifiable. The existing no-query route still lists up to 100 owned orders without a `lookupKey` property.


Historical reconciliation regressions retain a provider reference even when an initiation response contains a missing or untrusted checkout URL. This preserves investigation evidence without enabling another charge or restarting the removed provider.

Idle PostgreSQL connection failures are handled without terminating the process; readiness still depends on a successful database query. SIGTERM and SIGINT close the HTTP server, stop dispatch timers, await in-flight work, and close pools. A 10-second shutdown deadline prevents an indefinitely stalled stop.

## Staff commerce and private receipts

Commerce requires `PAMOFI_COMMERCE_ENABLED=true`, a valid delivery keyring and configured identity service authority. Every staff request resolves its current approved role, site scopes and MFA-completed session from identity. The browser never supplies an authoritative actor, role, price or commission. Admins create sites, publish immutable bundle versions and allocate stock. Agents sell only their own inventory at assigned sites. Support can inspect scoped sale/delivery history but cannot sell, reveal vouchers or resend them.

Approved MFA-verified administrators can prepare sales locations, inspect/create/publish catalogue versions and allocate reviewed stock while commerce is paused or a voucher keyring is unavailable. Approved staff can read their authorized site/inventory/history scope during a pause. These setup routes retain role, MFA and exact-origin mutation checks. Preparation does not enable sales, receipt pairing, vouchers, payments or network access; those operations retain their own gates.

| Route | Contract |
| --- | --- |
| `GET /v1/capabilities` | Explicit feature booleans, payment mode and demo flag; `deliverySms` checks the notification capability/mode, `networkAccess` shares the network route gate, `mobileCookies` remains false. |
| `GET /v1/sites`, `GET /v1/staff/sites` | Active commercial locations; administrators' staff list also includes paused locations. The staff list returns enabled/version and is scope-filtered. Creating a location does not configure a router. |
| `POST /v1/admin/sites` | Idempotent creation by body UUID or UUID `Idempotency-Key`. |
| `PATCH /v1/admin/sites/:id` | Approved-admin enable/pause of an existing sales location with `{enabled,expectedVersion,reason}` and UUID `Idempotency-Key`. Requires `salesLocationStatus:true` for new UI controls. |
| `GET/POST /v1/admin/bundles` | Inspect all versions or create immutable terms with a reason. |
| `PATCH /v1/admin/bundles/:id` | Publication and reason only. Change price/data/validity by creating a new version ID. |
| `GET /v1/staff/inventory` | Agent/site/bundle quantities. |
| `POST /v1/admin/inventory/allocations` | Approved target agent/site validation, one atomic stock increase and audit per admin idempotency key. |
| `POST /v1/staff/sales` | UUID idempotency key and `{siteId,bundleId,delivery,pairingCode?,phone?,payment}`; new sales require the exact cash confirmation below. One stock debit, sale snapshot, voucher and outbox event commit together. |
| `GET /v1/staff/sales` | Scoped history with `limit`, `offset`, `hasMore`, `nextOffset`. |
| `GET /v1/staff/sales/:id/receipt` | Private receipt for the owning agent or administrator. Ordinary sale responses omit the voucher. |
| `GET /v1/staff/sales/:id/delivery`, `POST /v1/staff/sales/:id/resend` | Sanitized delivery status and explicit idempotent resend to the same saved recipient. Unknown delivery remains blocked. |

All prices are integer minor units. `PAMOFI_AGENT_COMMISSION_BPS` defaults to zero and accepts 0–10000. Sales permanently snapshot price, currency, allowance, validity, site name and commission rate/amount. Allocation/resend reasons require 10–500 characters. Retry an uncertain sale with the same UUID key and immutable request; its committed response remains recoverable during a later delivery outage.

Apply `031_sales_location_status.sql` before the status route. Its version advances on actual `enabled` changes, including owner updates. The status action requires a decimal-string reviewed version and a trimmed 10–500-character reason; stale versions reject without mutation. Each accepted decision, including a no-op, records one append-only `commerce_audit` event with action `site.status`, actor, before/after and request identity. An exact retry returns its original response, even after a newer decision, without reapplying it. Clients refresh the list after replay. New cash sales check and lock location availability inside their transaction after prior-sale replay; a concurrent pause cannot admit a later new sale. A location pause preserves paid receipt/invoice/redemption recovery and stock/history, and never changes NAS trust or global commerce/network gates. Follow [the cash launch runbook](../../docs/CASH_HOTSPOT_LAUNCH.md) for physical commissioning and safe pause/drain.

Allocation retries check the committed request under the per-administrator idempotency lock before rechecking the target agent's mutable eligibility. A matching committed allocation remains recoverable after that agent is disabled or reassigned, without adding stock again. A new request rejected under that lock returns `allocation_agent_not_eligible` or `site_or_bundle_unavailable` after rollback; the web form permits correction. The former code requires a valid authoritative target record and is intentionally distinct from older deployments' pre-replay `agent_not_eligible` response. Identity outages, service authentication failures, malformed or mismatched target records, older ambiguous responses, and idempotency conflicts retain the saved request. Invalid new pairing/phone input is validated before saving a sale intent; pending sale bodies still replay unchanged.

New agent sales require `payment:{method:'cash',confirmed:true,amountMinor,currency}`. The amount and currency must equal the published server bundle terms; the browser cannot set the sale price. The transaction records the authenticated agent, server confirmation time and received minor units alongside the immutable sale. Receipts return `payment:{method:'cash',evidence:'agent_attestation',receivedMinor,currency,confirmedAt,confirmedBy}`. This records the agent's explicit cash attestation; it is not independent evidence of physical cash or a provider settlement. Demo sales retain `simulation:true`. Digital payment methods are never accepted by this cash-sale path.

Cash validation runs after the serialized idempotency replay lookup. A matching historical sale remains recoverable without a new confirmation and returns `method:'unrecorded',evidence:'unrecorded'` with null payment fields. Existing records are never backfilled as paid cash. New confirmed sales bind payment method, confirmation, amount and currency into their idempotency hash; changing or removing them conflicts with the original key. Missing/false/non-cash confirmation returns `cash_confirmation_required`; a new sale with a mismatched amount/currency returns `cash_amount_mismatch`. Both reject before issuance and stock decrement. Apply migration `025_cash_attestation.sql`; its trigger also prevents later changes to recorded tender evidence, agent, price or currency.

Customers create `POST /v1/receipt-pairings` with an idempotency key and show the random ten-character, five-minute code to an agent. Receipt or combined receipt/SMS sales consume the code atomically. Only the paired account can retrieve `GET /v1/receipt-pairings/:id` or redeem that voucher. SMS-only vouchers remain bearer codes, redeemable once into a customer account. Both delivery channels share the same voucher and at most one entitlement. `POST /v1/vouchers/redeem` requires a customer session, exact origin and rate limit; repeating a successful redemption by its owner returns the same entitlement. Redemption queues access without starting validity or connecting a device. Voucher/pairing codes never belong in query strings or request logs.

Configure `VOUCHER_DELIVERY_ACTIVE_KEY_ID` and `VOUCHER_DELIVERY_KEYS_JSON`, a JSON object mapping short key IDs to base64-encoded 32-byte AES keys. AES-256-GCM binds encrypted voucher codes, phone payloads and pairing codes to their record context. Each record stores its key ID. Rotation adds a new key and switches the active ID while retaining old keys needed for outstanding vouchers/receipts. Removing an old key makes those deliveries unavailable. No key is created or enabled by default.

Notification obtains transient message details from `GET /internal/v1/deliveries/:id` using a short-lived JWT with issuer/subject `notification`, audience `prepaid-access`, scope `delivery:read`, and separate `INTERNAL_DELIVERY_SECRET` of at least 32 bytes. Set `PAMOFI_SMS_DELIVERY_ENABLED=true` alongside `OUTBOX_DISPATCH_ENABLED=true`, a valid event secret, and the compatible notification worker; SMS is unavailable without that complete dispatch path. HTTPS is required outside demo/development. Sendai remains separately qualified and disabled by default.

## Quote status and browser boundaries

`POST /v1/orders` accepts `{bundleId,mode:'demo'|'checkout'}`. Demo is the backward-compatible default and unavailable outside demo/development. Checkout currently requires explicit local mock enablement. Idempotency binds the bundle and mode; checkout orders cannot use demo-confirm. In mock mode, `GET /v1/payments/methods` filters for an active location/published bundle; `POST /v1/orders/:id/checkout` verifies ownership, origin and a UUID idempotency key. Neither route offers an external payment method.

`GET /v1/orders/:id/status` reports `fulfillmentState` (`unconfirmed`, `fulfilled`, `reversed`, `pending_review`) and `entitlementRevokedAt`. Revoked entitlements have a null `entitlementId`. Historical `payment_confirmed` alone is not current fulfillment evidence. A consumed reversal or duplicate charge remains under review. Mock success/failure/reversal exercises the same reconciliation domain without a provider charge.

An expired quote can be safely replaced only after `POST /v1/orders/:id/expire-unused` with `{}` returns `{orderId,state:'expired_unused',safeToRequote:true,replayed}`. This customer-owned, origin-checked action locks the order against initiation, checks expiry using the server clock, rejects any prior payment attempt, charge or entitlement, and writes a durable fence. Its owned order ID is the idempotency identity. An initiating, unknown, pending or even failed attempt prevents this disposal path. The database also prevents a later attempt from an older process. Status reports `safeToRequote:true` and `order.expired_unused_at` only after committed closure; client-clock expiry alone never permits abandoning a payment intent. Apply migration `023_quote_expiry.sql` before this application version.

Rate-limit routes register after the Fastify plugin so their declared limits execute. `PAMOFI_TRUST_PROXY_CIDRS` defaults to empty, ignoring forwarded IP headers. Behind a controlled gateway, configure only exact private proxy IPs/CIDRs; wildcard trust, named ranges and `/0` are rejected. The public gateway must overwrite incoming `X-Forwarded-For` with its observed client address; trusted intermediate proxies may preserve that verified chain.

## Current usage snapshots

`GET /v1/usage` resolves the customer session and returns one PostgreSQL statement snapshot with `customerId` and server `asOf`. The read runs in a read-only transaction with a local two-second PostgreSQL statement timeout; errors roll back and release the connection, and the timeout does not affect financial transactions. It reports data allowance, not a monetary wallet. All byte counts are decimal strings, including aggregates larger than a signed 64-bit integer. The response is `no-store` and independent of the 100-row access-history page.

| Field | Meaning |
| --- | --- |
| `totals`, `active`, `queued` | Each contains `bundleCount`, `allowanceBytes`, `usedBytes`, `remainingBytes`. Totals include every current valid unrevoked bundle. Active means activated and still within validity; queued means unactivated and still within start-by. Exhausted current bundles remain included so 100% usage stays visible. |
| `lifetimeAccountedBytes` | Sum of the customer's recorded entitlement consumption, including expired/revoked history. |
| `reservationOutstandingBytes` | Open-grant reserved bytes less bytes already charged. This is reported separately: `remainingBytes` already subtracts consumption and must not be reduced by the reservation again. A Stop or uncertain session retains its reservation until reconciliation. If that entitlement expires or is revoked, its reservation can exceed the current remaining total; the reservation never makes expired allowance usable again. |
| `session` | Nullable current grant, including ownership-safe IDs, issued/deadline dates, reserved/charged byte strings, last received accounting time, disconnect/anomaly flags and derived connection freshness. |
| `lastAccountingAt` | Latest received accounting timestamp across this customer's grants, even after the last grant closes. It is not the device's instantaneous meter. |
| `hold` | `{active,reason,since}`. Remaining ledger allowance can be held pending review; displaying it must not imply that another connection is authorized. |
| `connectivity` | `none`, `pending`, `recent_accounting`, `stale`, `uncertain` or `held`. `session.connected` requires an active grant, recent accounting, an unexpired deadline and no hold/anomaly/disconnect request. Recent accounting does not guarantee an instantaneous router connection. |
| `accounting` | `expectedIntervalSeconds:60`, `staleAfterSeconds:90`, `pollAfterSeconds:5`. The RADIUS adapter requests 60-second interim accounting; delayed or missing packets can make displayed usage older. Five-second browser polling does not create five-second router measurements. |

For visible-card refresh, send optional `entitlementIds` as up to 100 comma-separated UUIDs. `entitlementUpdates` returns only matching owned rows plus the current grant's entitlement: `{id,consumed_bytes,activated_at,revoked_at,start_by,expires_at}`. Foreign and nonexistent IDs are both omitted. Immutable bundle terms stay on existing cards. The aggregate always includes all owned current bundles, regardless of selected IDs. The payload is bounded to at most 101 distinct updates.

Polling is limited to 60 requests per minute per resolved customer, with an IP fallback for unauthenticated requests. Customers behind one hotspot IP have independent authenticated budgets. Clients should poll only while visible/online, refresh on focus and relevant committed actions, and reject snapshots for a different customer. `/v1/access` and `/v1/orders` also return their resolved `customerId` so an account switch during a request cannot attach another customer's history to the previous account. On 401 stop polling and clear private data; on failure retain the previous timestamped snapshot as stale rather than inventing a zero balance. Migration `024_usage_accounting_index.sql` bounds the latest-accounting lookup; the open-grant lookup uses the existing partial customer index.

The isolated browser fixture can call `node test/fixtures/commerce.mjs account-usage --site UUID --agent UUID --customer UUID` only with the existing demo/development, loopback database and `PAMOFI_TEST_CONFIRM_ISOLATED=1` guards. It requires the exact `Browser fixture <UUID>` site and that simulated agent sale's paired customer/sole redeemed entitlement. It invokes the real grant/accounting functions with cumulative 1,000,000 upload and 2,000,000 download bytes; repeating it does not double-debit. Fixture removal permits only this exact labeled synthetic grant and refuses unrelated network state.

## Network reservations and operator review

Customer network access requires `PAMOFI_CUSTOMER_NETWORK_ENABLED=true`, `NETWORK_URL`, separate `INTERNAL_NETWORK_SECRET` (at least 32 bytes), and `INTERNAL_RADIUS_ENABLED=true` in demo or `PAMOFI_RADIUS_QUALIFIED=true` outside it. HTTPS is required outside demo. Network independently enforces its own gate and encrypted credential configuration. Customer routes are `/v1/network/sites`, `/session`, `/credentials` and `/disconnect` under the same prefix. A successful payment or queued entitlement is not connection evidence. Disconnect requests retain the reservation until accounting and independent router evidence permit closure.

`GET /v1/network/sites` returns `accessPoints: [{nasId,siteId,siteName,name,loginUrl}]`. The legacy `sites` list includes only sites with exactly one enabled NAS. A registration is not physical-service acceptance. New web/mobile clients require the gateway list, ask for an explicit choice when several are available, and send `{siteId,nasId,requestKey}` to `/v1/network/credentials`. The public schema accepts optional `nasId` for legacy clients, but accepts neither a customer identity, endpoint nor private replay authority. The response includes the exact site/NAS pair and registered HTTPS `/login` URL; clients verify all three before exposing credentials. Session/usage responses include `nasId`; legacy grants may return null, which allows status/disconnect but cannot prove a retry target.

A lost response retains the original browser request key and selected site/NAS. Legacy no-NAS retries remain tied to the original owned credential even if another NAS was subsequently enrolled. A fresh ambiguous request returns `409 nas_selection_required`. Deploy network, then prepaid, then the updated clients; a sites-only response leaves location selection unavailable with an explicit retry action. This selection/replay change adds no migration, while release preflight still checks the actual deployed baseline.

An open grant normally prevents credential preparation. The sole exception is replay of its exact existing credential while that customer's grant is still pending, unfenced, unexpired, without accounting/disconnect/absence/anomaly evidence or an account hold, and its own reserved entitlement remains usable. The service locks customer, grant and entitlement, derives the private credential ID from that grant, and holds the locks through the bounded private request. This request uses the distinct `network:credentials:replay` service scope, so older network versions reject it before issuance even if they strip its new body field. Ordinary issuance keeps the original `network:credentials` scope. The service rechecks current time and eligibility after locking and before returning the response. It cannot substitute another usable entitlement, issue a fresh credential under the reservation, extend access or authorize a new accounting-session ID. Active, uncertain and unknown-NAS grants retain the existing refusal.

Only authoritative `409 credential_expired` with no pending reservation permits the client to discard a saved request key and request fresh details on a later explicit action. Pending expiry returns `409 session_pending_or_active`; timeouts, mismatched replies and other uncertainty preserve the key. Replay does not close a reservation or prove that the router admitted the customer. Real NAS retry/session behavior remains a physical acceptance gate. Electronic payments remain separately disabled pending their integration and qualification.

MFA-verified administrators can list `GET /v1/admin/network/reviews` and resolve `POST /v1/admin/network/reviews/:id/resolve` using a UUID idempotency key, `expectedVersion`, decimal-string `finalUpload`/`finalDownload`, reason and evidence reference (10–500 characters). Resolution locks the customer and grant, requires fresh independent absence after the latest accounting/late-usage event plus credential fencing, and rejects another live reservation. Final counters must include all high-water/late-usage evidence and fit the existing reservation and entitlement. Only the additional verified bytes are charged; one append-only audit records the decision, and only that grant's account hold is cleared. Unknown usage cannot be guessed, written off or charged in full automatically. Periodic absence refresh does not invalidate an otherwise unchanged review version; new accounting/state changes do.

## Central router administration

Approved MFA-verified administrators use `/v1/admin/routers` and its explicit device/change subroutes. `PAMOFI_ROUTER_FLEET_ENABLED=true` enables reads when `NETWORK_URL` and `INTERNAL_NETWORK_SECRET` are valid; `PAMOFI_ROUTER_FLEET_WRITE_ENABLED=true` additionally permits previews/apply/rollback, subject to the network service's separate per-device policy. Neither requires the customer commerce or customer network launch gate. Capabilities are `routerFleet` and `routerFleetWrite`. Reconciliation and history remain available with writes paused.

The facade reuses the staff identity and origin checks, derives actor identity/version server-side, signs a fresh 15-second scoped service JWT, strips browser credentials, rejects unknown URL/body fields, bounds replies and projects only public DTO fields. Actor versions remain decimal strings. It makes no automatic retry after an upstream timeout; retrieve/reconcile the durable change ID. The public Vercel deadline can be shorter than a real router operation. See [Router fleet deployment and acceptance](../../infra/production/ROUTER_FLEET.md) and the OpenAPI paths for the preview/apply/reconcile/rollback contract.
